# apps/realtime

Guidance specific to `apps/realtime`. See root `CLAUDE.md` for commands, and `docs/architecture.md` for the shared split rationale, cross-cutting concerns, and test strategy.

`apps/realtime` owns everything client-facing: signaling gateway, `Room`/`Peer` membership state, chat, redis — it calls `apps/sfu` over REST for everything mediasoup-related.

- **`rooms`** — owns `Room`/`Peer` membership only (id, display name, and for `Peer` the ids+kinds of its producers for join backfill) — no mediasoup objects. `RoomsService` is Redis-backed (see `docs/adr/0002-redis-backed-room-state-for-stateless-realtime.md`); rooms are created lazily on first join (eagerly triggering `apps/sfu` MediaRoom creation via `SfuClientService`, same timing as before the split) and torn down when the last peer leaves — `SignalingService.leave()` calls `RoomsService.removePeer`/`closeRoom` and, right after, `SfuClientService.removePeer`/`closeRoom` to tear down the `apps/sfu` side too (see `apps/sfu/CLAUDE.md`). Its own `pendingRooms` dedup is a same-process-only optimization, not a cross-instance correctness mechanism — see the comment on `RoomsService.pendingRooms`. `closeRoom`'s empty-check-then-delete is one atomic step server-side (`CLOSE_ROOM_IF_EMPTY_SCRIPT`, `src/redis-scripts.ts`, run via `redis.eval`), closing the #24 race where a peer joining mid-teardown got wiped. The script is inlined as a string in `redis-scripts.ts` rather than a separate `.lua` file - `realtime`'s webpack builder doesn't copy non-TS assets into `dist`, so a standalone file never made it to the built output.
- **`sfu-client`** (`SfuClientService`) — the only thing in `realtime` that talks to `apps/sfu`, over `@nestjs/axios`, base URL from `SFU_SERVICE_URL`. Reconstructs a real `HttpException` from `apps/sfu`'s default Nest error body (`{statusCode, message}`) on any non-2xx response, so `WsExceptionFilter` surfaces the same message a client would have seen when this logic ran in-process.
- **`signaling`** — the only module that talks to clients (`SignalingGateway`, socket.io). Translates WS request/ack events (`join`, `createWebRtcTransport`, `produce`, `consume`, `pauseProducer`, etc.) into `rooms` membership updates plus `sfu-client` REST calls, and pushes server-initiated notifications (`newPeer`, `newProducer`, `producerPaused`, `peerClosed`, etc.) back out. `join`'s ack only returns `existingPeers`; producers of already-joined peers are backfilled to the new socket via direct (non-broadcast) `newProducer` emits right after the join ack, since that's otherwise the only event that tells a client about a producer. `SignalingGateway` is configured with `transports: ['websocket']` only — **clients must connect with `io(url, { transports: ['websocket'] })`** (or equivalent), since the default client tries HTTP long-polling first, and that polling handshake's session lives in-memory per instance, which the redis-adapter below doesn't cover. No LB sticky-session requirement follows from this, since there's no polling handshake state to keep pinned to one instance.
- **`chat`** — text chat backed by Redis Streams (`XADD`/`XRANGE`, capped with `MAXLEN ~`), keyed per room (`chat:<roomId>`), so history resumes from the last seen message ID. `ChatModule` only depends on `redis` and exports just `ChatService` (used by `signaling` for `leave()`'s history cleanup) - it doesn't provide `ChatGateway`, so importing it for `ChatService` alone doesn't also activate a client-facing WS surface as a side effect. `ChatGateway` (`sendChatMessage`, `getChatHistory` - needs `rooms` too, to look up the sender's display name) is instead a provider directly on `AppModule`, the same way `AppController`/`AppService` are, since nothing else needs to inject it.
- **`redis`** — single `ioredis` client behind the `REDIS_CLIENT` DI token; connection config from `REDIS_URL`/`REDIS_AUTH` env vars. Since issue #6, this is a hard dependency for `rooms` (every signaling op reads/writes Redis), not just an optional one for `chat` — see `docs/adr/0002-redis-backed-room-state-for-stateless-realtime.md`. `main.ts` also wires a `RedisIoAdapter` (`redis/redis-io.adapter.ts`) via `app.useWebSocketAdapter(...)`, attaching `@socket.io/redis-adapter` so `client.to(roomId).emit(...)` reaches sockets on any `realtime` instance, not just the one that received the request. It reuses the same `REDIS_CLIENT` as the pub client and a `.duplicate()` of it as the sub client — `duplicate()` opens a second live connection using the same `REDIS_URL`/`REDIS_AUTH` config, so each `realtime` instance now holds two Redis connections rather than a second independently-configured one.

Read `docs/sfu-signaling-design.md` before changing anything in `rooms`/`signaling` — most non-obvious decisions there are already justified and shouldn't be re-litigated without reading why first.
